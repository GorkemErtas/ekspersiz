## Low-risk optimization pass

- AI service: delay importing and initializing YOLO until first image request; loading remains singleton across concurrent first requests. Expect a slower **first** image request, but assistant-only sessions avoid allocating vision models.
- Assistant: serialize first-use embedding model initialization and RAG retriever creation to avoid duplicate memory allocations.
- Image validation: use float32 rather than float64 for temporary OpenCV Laplacian buffers; same quality-control logic and thresholds, minor numeric differences possible.
- Image upload: cap in-memory FastAPI read to maximum accepted payload plus one byte; oversized uploads still return HTTP 413.
- Backend: tune JVM heap to 128–768 MiB **default** (Railway JAVA_TOOL_OPTIONS can override); lower Hikari idle connections from ten to one and pool max to five (DB_POOL_MIN_IDLE / DB_POOL_MAX_SIZE can override).

## Validation before release

1. Run `cd ai-service && python -m unittest discover -s tests -p 'test_*.py'` and the repository's other existing tests.
2. Run `./mvnw test` and Flutter tests. Do not merge with failing tests.
3. Run a real model-weight smoke test: `GET /health`, assistant PUBLIC_WEB and APP_KNOWLEDGE, close + context image quality checks, one two-image damage analysis, and report creation.
4. Check **first image request latency** after idle/cold startup against Spring's HTTP timeout/retry policy. Increase timeout only with measured justification.
5. Load-test concurrent requests with real user flows, checking backend JVM RSS, heap, GC, OOM events, Hikari wait/timeout, AI RSS, and P95 latency.
6. After deployment, compare two **equally long and equivalently loaded** periods. Record per-service GB-min, active duration and request count, then calculate GB-min per request alongside idle GB-min.
7. Roll back by redeploying the prior image if inference latency, error rates or memory pressure regress. Restore previous JAVA_TOOL_OPTIONS / DB_POOL_* overrides where applicable.

**Note:** A reduced JVM heap is a candidate optimization, not a verified safe production limit. The dashboard's short peaks are not representative averages. No measured savings are asserted here.

## CI verification after the changes (2026-10-15)

- [AI tests + real model inference](https://github.com/GorkemErtas/ekspersiz/actions/runs/38763447241): successful. Seven focused lifecycle tests pass. Three committed YOLO weights load successfully, and vehicle / damage / vehicle-part models each perform real CPU inference on **synthetic noise**, not real vehicle photographs.
- [JVM startup with PostgreSQL + pgvector](https://github.com/GorkemErtas/ekspersiz/actions/runs/38763447158): successful. Spring Boot starts with `JAVA_TOOL_OPTIONS=-Xms128m -Xmx768m`, migrations run, `/api/v1/health` responds. On the **GitHub runner**, Java process RSS was about **402 MiB** at startup. This is not a load test.
- Observed GitHub-runner AI smoke metrics: **3.96 seconds** first image request; 87 ms vehicle model, 102 ms damage model, 108 ms part model (synthetic image); **497 MiB** process peak RSS. CPU throughput and memory differ on Railway.
- Maven tests: **167 total, 157 passed, 10 skipped, 0 failures** (CI unit-test run). Skipped integration tests must not be interpreted as passing.
- Real OpenCV headless package installation was hardened, because uninstalling the GUI package can leave `cv2` incomplete when the headless wheel is already installed.

## Release decision

Keep PR #7 in draft until real-image accuracy/latency, full integration tests, a realistic concurrency test under the Railway-sized CPU/RAM allocation, and available rollback/redeploy strategy are checked. Real AI Assistant responses, Google integration, payment workflow and push notifications are not exercised by the synthetic model smoke.

**No optimization has been deployed to the live Railway services; no Railway cost improvement has yet been observed.**
