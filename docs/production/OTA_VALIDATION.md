## PR #52 environment-contract hardening

The installed `eas-cli/package.json` reports **27.2.0**. Its actual compiled `build/update/utils.js` implementation, `environmentFlagNeededForSdk550OrGreater`, skips the flag check when `CI` or `EAS_BUILD` is nonempty. It also has an internal `EAS_UPDATE_SKIP_ENVIRONMENT_CHECK` override; deployment never sets it. Otherwise SDK 55+ requires the flag, and `promptVariableEnvironmentAsync` throws in non-interactive mode. `GITHUB_ACTIONS` alone does not bypass it. Thus the original master CI command was accepted by this exact CLI, but depended on an exception to the documented environment contract.

Staging now explicitly passes `--environment production`. The real CLI's dynamic project-config context overlays reloaded server values; its `loadServerSideEnvironmentVariablesAsync` caches that environment within the command. The new local snapshot guard, invoked at the very start of app config, checks effective config inputs, the production public-environment hash, exact Firebase bytes/base64/path and the sealed export digest. Native fingerprints are verified before/after export and immediately before CLI execution. The later CLI/SDK evaluations remain guarded. Snapshot metadata contains digests, not public key values, Firebase JSON or signing material, and is excluded from EAS/artifact uploads. The native runtime catalog and native signing workflow are unchanged; the new config guard itself participates in fingerprinting.

Hardening validation:

- Full application suite: **23 suites / 137 tests passed**.
- Full release/CI suite: **44 tests passed**, including command-flag enforcement, configuration/Firebase/export drift and invalid/failed publication responses.
- **10 real CLI integration preflights passed** against the installed command, Oclif flag parser, dynamic public/private Expo configuration and real server-environment loader. Cases: missing flag locally, GitHub flag alone, both CI exceptions, valid explicit production environment, public/Firebase/variant/bundle drift, and environment-fetch failure. Valid explicit production execution performs one environment query (cached thereafter); drift fails before the upload boundary.
- Preflights use isolated synthetic projects and mocked authentication/server reads. Configuration writes, bundling, network and publication/upload methods are trapped, and execution deliberately stops before upload. No command publishes an update. This verifies actual CLI control flow, not live account configuration or end-to-end delivery.

It used only synthetic public Firebase/key metadata. Export SHA-256: `6e1cf8f7585d4e88d72a35c9f26fb8deb267fa36e30ebbe469ed092de1a497d6`. ## Safety and failure evidence

Tests cover disabled/missing/invalid OTA opt-in, wrong project/channel/package, unsafe API or public values, Firebase service accounts, native release version reuse, missing signing inputs, UI/native/unknown-path classification, unregistered runtime, public-environment drift, wrong update group, cross-channel routing, invalid rollout, missing Expo/GitHub credentials, missing required reviewers and untrusted source runs/artifacts.

The staged publisher exports once and calls EAS with the validated export directory. Production and rollback tests assert republishing the source group without exporting again. A rollback must explicitly select previous accepted evidence and use 100 percent. Ambiguous network failures never cause automatic retries or rollback; pre-publication and bootstrap audit receipts preserve the result for investigation.

Only protected publishing steps receive `EXPO_TOKEN`. PR validation has no Expo token, signing inputs or Play credentials. Production uses a required-reviewer environment, validates its policy through GitHub, checks the exact successful master source run and unexpired artifact, and rechecks native/environment/remote-group identity before republishing. Personal Expo tokens inherit account permissions; channel isolation is enforced by the reviewed tooling and routing, not by claiming channel-scoped tokens.

No custom runtime reload code was introduced. Built-in startup checks, zero launch wait, embedded fallback and anti-bricking behavior remain enabled. Automated config tests establish these settings; they do not replace device testing of offline/interrupted downloads or store/auth/payment flows.
